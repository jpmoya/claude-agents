# Orchestrate (headless)

The orchestrator must outlive this session. Subagents don't: they run inside the parent process and die on compaction, restart, or exit. So the orchestrator is launched as its own `claude -p` process via the script in this skill, and this session only reads its status.

**Skipping mockups:** the mockup gate is skip-by-default now (#701) — it never pauses unless JP's `**[jp] REVIEW MOCKUPS**` first line is on the issue. JP's exact `**[jp] SKIP MOCKUPS**` first line always wins over a standing `REVIEW MOCKUPS` and skips the gate wherever it lands as an issue comment — any author, any channel (Slack relay, a direct GitHub comment, an in-session post; #700, no per-source trust distinction, no quote line required). Neither marker is ever read from a brief, launch text, the issue body or a label — those are ignored.

**Relaying an in-chat approval:** when JP approves mockups (or gives a `go` on a JP-only gate) in the interactive session's own conversation, the session posts a comment whose line 1 is exactly `**[jp] MOCKUPS APPROVED**` (or `**[jp] GO**`) and line 2 is `JP said: "<JP's words, verbatim>"`, on each ticket he approved — never `[delivery-lead] JP CONFIRMED` for these. Never from a brief, launch text, Slack, issue body or label.

## Launch

```bash
~/.claude/skills/orchestrate/launcher.sh <repo-path> <issue> [extra instructions]
```

- `<repo-path>`: the repo's main checkout (e.g. `~/dev/benjis-ops-tool`, or `~/benjis-ops-tool` on Clog). The script resolves `owner/repo` with `gh`.
- Extra instructions are appended to the orchestrator's prompt verbatim — use them for context it can't read from the issue (e.g. "config blocker resolved, retry from test-writer").
- One orchestrator per issue; the script refuses to launch a second while the first is alive.
- Max 3 concurrent orchestrators (VM has 3.7GB RAM, 1200MB memory floor). If all slots are full or memory is low, the launch is queued automatically and the supervisor launches it when capacity is available. `status` shows both running and queued.
- It prints the PID and log path (or "queued" if at capacity). Report to JP and stop. Do not poll, do not wait, do not tail in a loop.

## Supervisor (one cron tick does everything)

`supervisor.sh` runs every 2 minutes on both machines — VM from cron on even minutes (`*/2`); Mac from a launchd user agent on odd minutes (`~/Library/LaunchAgents/com.jp.pipeline-supervisor.plist`, `StartCalendarInterval`), because macOS cron jobs have no keychain access and `claude -p` reports `Not logged in` (2026-09-13). Both log to `~/logs/pipeline/supervisor.log`. Mac power: dispatch also runs on battery above `BATTERY_MIN_PCT` (30), and a live run holds `caffeinate -i`. A loop-cap hold is relaunched automatically (step 1b) once a `[delivery-lead]` `DECISION`/`JP CONFIRMED` is posted after it. Each tick, in order, at most one launch:

1. **Restart** exited orchestrators whose latest marker is not terminal, with backoff (2/5/15/30 min; short-lived exits count as transient with their own longer table using per-launch timing via `.launched-at`). After 3 restarts without marker progress or 6 total it posts a `**[supervisor] NOTE**` on the issue and parks the run (`held`).
2. **Drain** the local queue when a slot is free.
3. **Labels:** drop `agent-in-progress` on issues this machine finished (`done`: DEPLOYED / APPLIED / closed), parked (`held`: MOCKUPS PENDING APPROVAL, AWAITING GO, BLOCKED after the 20-min grace, or escalation), JP stopped, or dead with no pending relaunch in the queue.
4. **Label reconciliation:** scan `DISPATCH_REPOS` for open issues carrying `agent-in-progress` with no local pid file and no queue entry. If the issue's last comment is older than 30 minutes, clear the label — it's orphaned (the machine that owned it died or lost `/tmp`). This prevents the "running elsewhere?" deadlock where no machine can claim a dead run.
5. **Shared dispatch:** if this machine's `DISPATCH_REPOS` is set, list open `agent-go` issues without `agent-in-progress` across those repos and launch the first one it has capacity for, in release order (milestone `vX.Y.Z` ascending, compared numerically; then issue number ascending; no, `staging` or non-version milestones sort last; cross-repo priority stays `DISPATCH_REPOS` order) — after posting a claim NOTE (`**[supervisor] NOTE** claim: <host> <ts>`), waiting 15 s, and confirming its claim is the earliest in the last 10 minutes. Lost claims are logged and skipped. On a Mac, dispatch runs only on AC power (restarts and drains always run).

**Scheduled triggers (#769).** GitHub's `schedule:` cron is unreliable (the app repos' auto-release router, every 5 min, went silent for ~6.5 h on 2026-11-19), so a separate cron job (`* * * * * ~/.claude/skills/orchestrate/scheduled-triggers.sh run >> ~/logs/pipeline/scheduled-triggers-cron.log 2>&1`, every minute, its own lock, independent of the supervisor tick and its lock; a tick takes 6-60 min, which is why the router no longer rides on it, #783) runs `scheduled-triggers.sh`, which fires the schedule-only workflows listed in `scheduled-triggers.conf` (`<owner/repo> <workflow file> <interval minutes> [input=value ...]`; one line per workflow, no code change to add one) with `gh workflow run`; the jobs still run on the self-hosted runners and the `schedule:` triggers stay in the app repos as a fallback. Off unless `SCHEDULED_TRIGGERS_ENABLED=1` in that host's `config.local.sh` (set it on the VM only); `install.sh` adds the cron line only where that is set (one line, idempotent, removed again when it is off) and `host-drift.py` reports it missing. `supervisor.sh` does not call it. A workflow is due when this host's last-dispatch stamp (`$PIPE/scheduled-triggers/`) is older than its interval (local read, zero `gh` calls when nothing is due); for each due one a single `gh run list --workflow` read skips it while a run is queued/in progress or one started within the interval (that is what stops the VM and Mac, and GitHub's own cron, from double-firing; the per-host lock only covers overlapping passes on one host), then one `gh workflow run` (no `--ref`: the default branch). Every dispatch appends `<epoch> <repo> <workflow> ok|failed` to `~/logs/pipeline/scheduled-triggers.log` (a failure once per workflow per hour, also to the Slack webhook with release/environment/route tags, and it never stamps the workflow as fired). Each gh call is killed after 30 s, and a failed read or dispatch backs that workflow off for one interval (max 30 min); an in-progress run counts as a fire, and the beat also carries `tracked_since` so a router that never fires at all still alerts. Never add a workflow whose dispatched run differs from its scheduled run without an input that mirrors the schedule (see the notes in the conf). The beat publishes the per-workflow last fire (`scheduled_triggers[]`); the status page raises "The release router for <owner/repo> has not fired in N minutes" (the beat carries `full_repo` next to the alias `repo`; the beat itself still goes out on every supervisor start, so a long tick does not blind it) when an `auto-release*` entry is older than 3 intervals plus the 10-minute keep-alive allowance.

Config: shared defaults in `skills/orchestrate/config.sh` (labels, caps, backoff). Per machine, untracked, `~/.claude/pipeline/config.local.sh` holds the repo lists.

- **Dispatch eligibility** is per machine: `DISPATCH_REPOS=("owner/repo:/local/checkout" …)` lists the repos whose `agent-go` issues this machine's supervisor may launch — VM: casa-verde-site, rfp-finder, ops tool; Mac: those plus sales tool and Business-Intelligence. Empty list = that machine only runs what is launched on it by hand.
- **Scan coverage** is separate and lives on the one `SCAN_BACKLOG=1` machine (the VM): the hourly `scan-backlog.sh` labels unlabelled open issues `agent-proposed` across that machine's `DISPATCH_REPOS` plus `SCAN_ONLY_REPOS=("owner/repo" …)`, each repo at most once. `SCAN_ONLY_REPOS` (default empty = scan exactly `DISPATCH_REPOS`) is read by the scan alone — the supervisor and the launcher never see it, so listing a repo there never makes a machine dispatch it. The sales tool is scanned on the VM through `SCAN_ONLY_REPOS` and dispatched only from the Mac. Business-Intelligence is in neither the scan nor any automatic queue — it is on no list of the scanning machine, so nothing ever proposes it, and the Mac launches a Business-Intelligence issue only after JP himself adds `agent-go`.

Label rule: `agent-go` = "approved, not launched anywhere yet"; launching anywhere swaps it for `agent-in-progress`; the supervisor removes `agent-in-progress` when the run is done or parked. To run a parked issue again, relaunch by hand or re-add `agent-go`.

`agent-go` is the only label `supervisor.sh` itself checks before launching a ticket. Everything else (`goal: <title>`, `fast-lane`, `infra`, `bug`, `user-feedback`, `source:sentry`, `agent-proposed`) is classification that routes a ticket once it has `agent-go` — it does not get a ticket picked up by itself. Four paths add `agent-go` with no human click, each gated by a config check inside the script that grants it:
- Staff feedback intake (`intake-labels.sh`): `INTAKE_AUTO_GO` (default on) — bug reports from JP/the app get `agent-go` immediately; Sentry-sourced bugs instead check `SENTRY_AUTO_GO` (on since #678: a triaged Sentry bug goes straight to the fix pipeline; `SENTRY_AUTO_GO=0` in `~/.claude/pipeline/config.local.sh` is the kill switch and makes them wait for JP via `agent-proposed`). The supervisor, not the intake agent, sets the final labels of a Sentry ticket from the handoff marker (`sentry_label_gate`): `agent-go` stands only on an open ticket whose newest `[intake]` marker is `TRIAGED BUG`. With the switch on, the supervisor writes `sentry-auto-go` in the same label write as `agent-go` (the helper prints both; the intake agent cannot set either), and at most `SENTRY_AUTO_GO_DAILY_CAP` (default 3) such tickets are launched per repo per rolling 24h on a host: `launcher.sh` refuses the next one with exit 3 (`sentry launch cap reached for <owner/repo> (<n>/<cap> in 24h)`, `--force` does not bypass, `SENTRY_CAP_BYPASS=1` in the environment does) and the supervisor leaves it queued with its labels until the window frees. The cap bounds new tickets: any relaunch of one that already launched in the window (an automatic restart, or a hand / delivery-lead relaunch after a hold) is neither refused nor counted again (`COST_CEILING_USD` bounds each ticket). A `sentry-auto-go` ticket that also carries `ci-critical` (#781, a CI or release-pipeline fix that must not queue behind error triage) is exempt: the supervisor and `launcher.sh` skip the cap for it (an unreadable launch log does not block it either), it is not counted (its `sentry-launches.log` line ends in `exempt`), and a normal Sentry ticket of the same repo and tick still waits. The label alone decides, and only on a `sentry-auto-go` ticket. While the cap holds tickets the supervisor leaves `$PIPE/sentry-cap-held.<repo>.json` and `report-status.sh` publishes `sentry_cap` (`sentry-cap-status.sh` recounts the window, so it is empty under the cap); the status page lists them as "Held by Sentry cap, resets HH:MM CET". A Sentry ticket released by hand after intake is done carries no `sentry-auto-go` and is never throttled; while an intake run still owns the ticket, an `agent-go` without `sentry-auto-go` is removed.
- Goal approval (`goal-lib.sh`): once JP sets `go:true` on a goal, every open ticket that carries that goal's `goal: <title>` label always gets `agent-go` — no further check.
- Start-gate promotion (`supervisor.sh`'s promote loop): when a ticket's blocker is closed, or shipped to the integration branch (`dep-shipped.sh <owner/repo> <N>`: its PR merged into `staging`, or the default branch where there is no `staging`), the ticket inherits the blocker's approval and gets `agent-go` automatically. A run that stopped on a start-gate is held with the unmet refs in `orch-<key>.startgate`; the supervisor re-checks them every 30 min and relaunches it once they are met.
- Backlog scan (`scan-backlog.sh`): a new issue that already carries an approved goal's label gets `agent-go` on sight; otherwise it only gets `agent-proposed`.

- **Per machine.** `~/.claude/pipeline/state` (pids, queue, tombstones) is local; the only shared state is the issue's markers and labels. The launcher refuses an issue that carries `agent-in-progress` and isn't owned here ("running elsewhere?"); A hand launch also posts a claim, waits `CLAIM_SETTLE_SECS` and refuses (`lost claim to <host>`) unless its claim is the earliest in `CLAIM_WINDOW_SECS` (#217). `launcher.sh --force <repo> <issue>` skips both checks — the deliberate takeover, e.g. a handover after the other machine's run was stopped.
- `stop` writes a tombstone — the supervisor will not auto-restart a manually stopped orchestrator.
- A manual `launcher.sh <repo> <issue>` clears tombstones and restart state and supersedes a queued entry.
- `status` shows the state: `running`, `exited (will auto-restart)`, `stopped (manual)`, `held (needs JP)`, or `done`; `!! ALERT` lines say why something is held.
- **GitHub API budget (`gh-budget.sh`, sourced by `config.sh`).** The 5000/hr quota is shared by everything on the account, and the pipeline itself used to exhaust it. Every script's `gh` is now a function that (1) logs each call to `~/logs/pipeline/gh-calls.log` (`epoch file:function class call|hit|skip subcommand-or-endpoint`; rotated by `rotate-logs.sh`; top callers: `cut -d' ' -f2 gh-calls.log | sort | uniq -c | sort -rn`), (2) reads `gh api rate_limit` (free) at most every `GH_QUOTA_TTL_SECS` (60) into `$PIPE/gh-quota` and skips work by class: below `GH_QUOTA_OPTIONAL_BELOW` (1500) optional work (status reconcile, stale digest, scan-backlog, held-goal evaluation, worktree sweep), below `GH_QUOTA_ESSENTIAL_BELOW` (300) everything except essential work (restarting live runs, draining queued launches), at 0 every call until the reset (the supervisor tick just ends); each tick logs `gh-quota remaining=N reset=<Europe/Madrid time> graphql=M`, and (3) reuses issue/comment/milestone/goal-registry reads for `GH_CACHE_TTL_SECS` (60; flushed by any write and at each tick start; claim reads bypass it). Step 3e and step 4 now run at most every 300 s / 600 s (`GH_PROMOTE_DEFERRED_SECS`, `GH_LABEL_RECONCILE_SECS`). All knobs live in `config.sh` (override in `config.local.sh`); `GH_BUDGET_ENABLED=0` turns it all off. Work classes are set with `gh_class essential|normal|optional`.
- **Tick timing and budget (#796).** A tick that runs long starves everything after it, so: the goal step (registry sync, goal keep-alive, `goalqueue.json` for the status page) runs first, right after the since-sync; the worktree sweep (every 30 min) is a background job with its own lock (`$PIPE/worktree-sweep.lockdir`) and a `WORKTREE_SWEEP_BUDGET_SECS` (240) time budget, its stamp written at launch; each tick logs `[tick-timing] stage=<name> secs=<s>` for every stage over 5 s plus `stage=total` (read it with `grep tick-timing ~/logs/pipeline/supervisor.log`). `TICK_BUDGET_SECS` (480, soft) makes the pure housekeeping (label reconcile, stale digest) skip with a `[tick-watchdog]` line; every stage that starts or restarts work always runs. `TICK_HARD_SECS` (840) stops a stuck tick cleanly (exit 0, lock released). Held runs whose recorded repo directory no longer exists are skipped with one `[held-skip]` summary line instead of a failed read each, and a failed issue read is remembered for `HELD_READ_FAIL_TTL_SECS` (300). The status page already shows how old the goal data is (`goals_as_of`, #795), so this change only makes the data fresher.

## deliver.sh (goal-bound delivery lead)

`skills/orchestrate/deliver.sh` registers a goal (a registry issue on GitHub) as `queued`; the supervisor starts the delivery lead (`delivery-lead`) of the next queued goal when a goal slot, memory and power allow, every earlier goal (registry `priority`, 1 first, then `order`, then issue number) is delivered, stopped or waiting on JP, and this host is eligible (VM first, the Mac after two ticks; `--host` pins). The two hosts race with a `**[supervisor] NOTE** claim:` comment on the registry issue, settled by `claim_winner`. `--now` launches one cycle at once (hand use). Registering a milestone or `#N` goal is JP's go (#410): the block records `go:true`, open in-scope tickets get `agent-go` (never Business-Intelligence; `source:sentry` only with `--include-sentry`), and each sync grants later arrivals. A `milestones:all` goal grants nothing without `--approve-all`. Keep-alive and completion belong to the supervisor, not to the agent.

**One goal at a time (`GOAL_SERIAL=1`, the default since 2026-10-30).** Both hosts share ONE goal slot: a queued goal starts only when no other goal is active on either host (registry state, so the VM and the Mac agree), in the usual order (`priority`, then `order`, then issue number). The slot frees when the goal is delivered, stopped, held or waiting on JP. A goal coming back from held or waiting on JP rejoins the queue instead of relaunching, and an extra active goal (a `--now` or `resume` hand launch, or one already running when the mode was switched on) finishes its current cycle and then returns to the queue; nothing is killed and in-flight tickets keep running. The one active goal still uses both machines: the host without its lead dispatches its `agent-go` tickets (supervisor step 5) even with `SHARED_DISPATCH_ENABLED=0`, and the claim comment keeps each ticket on one host. If the host running that goal's lead is down, the queue waits for it, but its tickets keep running on the other host. A hand launch next to it overlaps only until its own cycle ends. Standing feedback goals (`owner/repo:feedback`) start in their queue turn like any goal, then run beside it and never hold the slot (`GOAL_SERIAL_FEEDBACK=1` makes them take it too). Revert: set `GOAL_SERIAL=0` in `skills/orchestrate/config.sh` and sync both hosts (one host on each setting breaks the guarantee); that restores the old per-host behaviour (up to `MAX_GOALS` leads per host) exactly.

**A goal that cannot be read blocks nothing but itself (JP, 2026-11-19, #793).** A project goal whose scope read fails (closed or missing project, a parse failure, GitHub down) leaves a marker `$PIPE/goal-proj-err-<owner>_<n>`; for `GOAL_SCOPE_ERR_SECS` (600) the queue computation (`_goal_queue_jq`) leaves that goal out of the slot and the candidate choice, so it neither holds the slot nor stands in front of the queue and every other queued goal starts in the same priority order; a full good read clears the marker (a one-item `--meta` read does not; the marker also expires by itself), and the start step probes a candidate's scope (`--meta`, one item) before it claims, so an unreadable one is skipped instead of started. A registry entry whose goal block cannot be read is skipped the same way (still listed as `unreadable` in `goalqueue.json`). A failed `gh` call is retried twice (`GOAL_PROJ_RETRIES`, `GOAL_PROJ_RETRY_SECS`) before it is logged; a parse, closed or missing-project answer is final. The status page shows each as an amber "<goal> cannot be read (reason); it is skipped, other goals unaffected". The markers are files on each host, so while only ONE host cannot read a project that host frees the slot and the other still sees the goal holding it: two goals can then run side by side (the overlap checks below still protect shared tickets; the "registry state, so the VM and the Mac agree" guarantee above does not hold during a one-host read failure). Unchanged: a readable ACTIVE goal still holds the one slot, the overlap checks between two live goals that share tickets (`deliver.sh` register, `_goal_fb_covered`) still refuse when the other live goal's scope cannot be read, and an unreadable REGISTRY (the list itself) still fails closed.

```bash
~/.claude/skills/orchestrate/deliver.sh <goal> [--now] [--host <name>] [--priority <n>] [instructions...]   # register (queued); --now also launches one cycle
~/.claude/skills/orchestrate/deliver.sh priority <goal|id> <n>   # change a goal's priority (1 starts first)
~/.claude/skills/orchestrate/deliver.sh project <goal|id|all> [--create]   # bind/sync the goal's GitHub Project (Mac only: needs the gh `project` scope)
~/.claude/skills/orchestrate/deliver.sh status [goal|id]           # one line per goal (open, plus closed within 7 days)
~/.claude/skills/orchestrate/deliver.sh stop <goal|id>             # label goal-stopped, close the registry issue, kill the local cycle (idempotent)
~/.claude/skills/orchestrate/deliver.sh resume <goal|id> [--here] [--now]  # reopen a stopped/held goal; --here re-pins it to this host; --now also launches one cycle here (forces a queued goal, see below)
```

Each goal has a GitHub Project (v2, "Goal: <title>", fields copied from project 1) that mirrors it: the registry block's `project` field records it, `deliver.sh register` creates one, the supervisor sync binds an existing "Goal: ..." project (by title or items) and keeps tickets and Status current, a delivered or stopped goal closes it, and the lead's brief and the status-page goal link point at it. All `gh project` calls live in `goal-project.sh`; hosts whose gh token lacks the `project` scope (the VM: `gh auth refresh -s project`) skip it, and a project error never blocks a goal.

- **Goal kinds:** `owner/repo:milestone:<number|exact title>`, `owner/repo:milestones:all`, `owner/repo:feedback`, `owner/repo#N`. Also `label:<name>` with `--repos` (cross-repo) and `project:<owner>/<number>` (#736; alias `owner/repo:project:<number>`): a GitHub Project whose issue items (open and closed, any repos; draft and pull-request items ignored) are the scope, no milestone or label needed. The state is the issue's own, never the project Status. A closed, missing or unreadable project (or a host whose gh token lacks the `project` scope) fails closed: it is never an empty scope. The registry block records the derived `repos` and the `scope_project`; the goal never gets a mirror project of its own and the mirror sync never renames, closes or edits the project. Conversely a project that is some goal's scope is never adopted as another goal's mirror (by title or shared items), and a live goal's mirror project is refused as a scope.
- **Staff-feedback goal (`owner/repo:feedback`, #472):** a delivery lead bound to the repo's `user-feedback` tickets that no other live goal (queued, active, held or waiting on JP) covers, whatever their milestone (closed ones count as delivered; #517: the product-manager gives every ticket a milestone, so the old "no milestone" rule matched nothing). It yields: a ticket leaves its scope while another live goal covers it, and registering or resuming another goal never overlaps it. The yield is immediate for the running cycle too (#527): a feedback cycle launched with a ticket another goal has since taken is ended (on the same host at once by `deliver.sh`, on the other host at its next goal sync, at most `GOAL_SYNC_SECS`) and relaunched straight away with a fresh brief, counted as neither a crash nor a launch failure. A stop never hands tickets back on its own (#527): `deliver.sh stop` records the goal's open tickets in its registry block (`stopped_open`) and they stay out of the feedback scope, however old the stop, until JP runs `deliver.sh release <goal>` (or resumes the goal, or registers a new goal over them); a stop that cannot list them makes the feedback scope on that repo unreadable until the release. Stops made before #527 hold nothing. The scope read fails closed (logged on route `goal-fb-scope`, no lead cycle) on any unreadable or malformed live or holding registry entry, stored spec, repo name or scope. When an in-scope ticket is blocked on an open ticket that no live goal covers and no stopped goal holds, and that ticket already carries `agent-go`, the lead adopts it by adding `user-feedback` (nothing else changes; a blocker without `agent-go` goes to JP through the needs-JP request, and the lead never parks the in-scope ticket `needs_jp` to ask JP to queue it, #566; the supervisor does this adoption itself every 5 minutes with no LLM, `goal_fb_adopt_blockers` in goal-lib.sh: at most 5 per pass, only a ticket already carrying `agent-go` and no `agent-stop`/hold label that an in-scope ticket names after `Depends on` / `merge-gate` / `blocked by` (first #N only) or in its latest `[delivery-lead]`/`[deployer]` BLOCKED comment, logged as `[adopt] #N adopted into the feedback goal: blocker of #M`). It clears their technical blocks (full disk, red or flaky CI, merged-but-deploy-unconfirmed, malformed or missing delegated decisions) and surfaces only product/business calls and JP-only items. It grants no `agent-go` and touches no label or milestone: feedback tickets keep dispatching through supervisor step 5 (the `SHARED_DISPATCH_ENABLED=0` feedback exception), so the lead and the dispatcher never compete. It follows the ordinary goal rules: the supervisor keeps the lead alive, parks it as held without progress (it resumes when a ticket changes) and closes the goal when every scope ticket is closed; register it again when new feedback arrives after that. Default registration: `deliver.sh Benjis-Plants/benjis-ops-tool:feedback` and `deliver.sh Benjis-Plants/benjis-sales-tool:feedback`.
- **Overlap refusal:** a new goal that shares a ticket, or a repo with a `milestones:all` goal (for a project goal its repos are those of its items), with a live goal (open registry entry: active, held or waiting on JP) is refused, and the error names the live conflicting goal. Repos are compared through `repo_canon` (#527), so a goal stored under a pre-rename slug conflicts with the same tickets under the new slug. It fails closed when the registry is unreadable or does not parse, or a repo name cannot be resolved.
- **Both machines (`--hosts`):** one lead per goal, but its tickets spread. `--hosts both` (default; field absent = both): the lead's host dispatches the goal's tickets through the lead, the other host's supervisor (step 5) dispatches them too, and the claim comment guarantees a ticket never runs on both. A goal not started yet (still queued) dispatches nothing anywhere. `--hosts mac|vm` confines the whole goal (lead start and tickets) to that machine. Label goals only.
- **Host pin:** a goal is pinned to the host that registered it; another host's supervisor does not run it. `resume <goal> --here` re-pins it to this host.
- **State words in `status`:** running, between cycles, held, waiting on JP, stopped, delivered.

## Registering a goal (JP, 2026-11-18: a GitHub Project, one name everywhere, go explicit)

Every goal is a GitHub Project whose issue items are the goal's tickets (#736); the registry (GitHub issues labelled `delivery-goal` in jpmoya/claude-agents, created by `deliver.sh`) is the one list of goals, and the status page shows exactly the registered goals, never a bare project. `deliver.sh` registers a project spec only: milestone (`owner/repo:milestone:...`, `:milestones:all`), label (`label:...` or `--repos/--title`) and ticket (`owner/repo#N`) goals are refused with this recipe (the standing `owner/repo:feedback` goals are the one exception, below), and `hooks/block-nonproject-goal.sh` (PreToolUse on Bash) stops the call before it runs. Existing goals keep working (`status`, `stop`, `release`, `resume`, `priority` are never blocked).

```
gh project create --owner Benjis-Plants --title "Goal: <short human name>"   # prints the project number <n>
gh project item-add <n> --owner Benjis-Plants --url <issue URL>               # once per ticket (any repo)
~/.claude/skills/orchestrate/deliver.sh project:Benjis-Plants/<n> --go|--no-go [--priority <n>] [--now] [instructions...]
```

**The go choice is JP's, never the session's.** The session MUST ask JP and may never pick it itself, guess it from context or default it; `deliver.sh` refuses to register without `--go` or `--no-go` and the hook blocks the command with the question.
- **Go** (`--go` / `--no-go`, exclusive): "ask JP: go true or go false?" `--go` = go true: every ticket in the goal's scope inherits `agent-go` (granted at registration and by every sync). `--no-go` = go false: no `agent-go` is given and each ticket needs its own from JP. `deliver.sh status` shows `go=true|false|unset` for every goal (`unset` = a block with no go field, i.e. the two standing feedback goals, whose behaviour is unchanged).
- **Priority** (`--priority <n>`) is optional. With none the goal records no priority and queues in registration order (the queue key falls back to `order`, then the issue number); `deliver.sh priority <goal> <n>` (or `--after`/`--before`) reorders it later. A given number is a place in the start order (1 starts first). The status page shows the priority number only when one was explicitly set.
- **Priority only orders the queue.** Priority 1 (or any queue position) does NOT make a goal start immediately or take the goal slot from a goal that is already running. To start a new goal right away you must force it: stop the goal that holds the slot (`deliver.sh stop <goal>`; a held or waiting-on-JP goal does not hold the slot), or register with `--now` (runs one cycle by hand; under `GOAL_SERIAL=1` a `--now` goal that does not hold the slot returns to the queue after that cycle). To force one cycle of a goal that is already registered and queued, without stopping the slot holder, run `deliver.sh resume <goal|id> --now` (#784): it launches one cycle here, the goal stays queued with its place and priority, and under `GOAL_SERIAL=1` it returns to the queue after that cycle; a launch failure leaves it queued and alerts Slack. It does nothing to an active or waiting-on-JP goal ("already active"), and a held or stopped goal is reopened first, as `resume` does. There is no preempt command: to take the slot itself (not run beside the holder), stop the holder.

**Naming convention.** One string names a goal everywhere: the project is `Goal: <Name>`, `deliver.sh` creates the registry issue as `Goal: <Name>` from the project's name, and the status page shows `<Name>`. `<Name>` is a short human name (at most 80 characters): no repo path, no `#N`, no spec syntax (`:milestone:`, `:feedback`, `label:`), no second `Goal:` prefix. `deliver.sh` refuses to register a project whose title breaks it (rename with `gh project edit <n> --owner <o> --title "Goal: <Name>"` first) and the hook rejects a `gh project create|edit --title "Goal: ..."` that breaks it. `owner/repo:project:<n>` is an alias of `project:<owner>/<n>`. The host's gh token needs the `project` scope (`gh auth refresh -s project`). `GOAL_ALLOW_LEGACY_REGISTER=1` (in `deliver.sh`'s environment) lifts every refusal above for legacy tooling only (and restores the old defaults: go true, last priority); the hook honours it only from its own environment, never from a prefix inside a session's command.

**Status page = registry.** `build-runs-json.py goals` lists the goals the supervisor sync copied from the registry into `goalqueue.json` (open, queued, the 5 most recently closed), each under its registry name (`name`: the issue title without `Goal: `; the block title when the issue title only repeats the spec) and, when explicitly set, the registry's own `priority`, in queue order (priority, then order); a slot-exempt feedback goal is listed after them as "runs alongside" with no number. A project is only the link of the goal it is bound to; an open `Goal: ...` project with no registry issue is not a row, and a local goal cache the registry does not list is not a row. A host that never synced (no `goalqueue.json`) keeps its local rows. Under `GOAL_SERIAL=1` each row also carries `slot` (from the same registry read as the slot logic: `holds` = the goal holding the one goal slot, shown with its host; `waits` = a queued goal; `alongside` = a slot-exempt feedback goal), drawn as the icons in the legend at the top of the Goals table.

**Feedback goals keep their spec.** The standing staff-feedback goals stay `owner/repo:feedback`: goal-lib's slot exemption (`exempt`, `goal_slot_exempt`, `GOAL_SERIAL_FEEDBACK=0`) and the per-repo scope (every `user-feedback` ticket no other live goal covers) are keyed on that spec, so re-registering one as `project:<owner>/<n>` would make it a normal goal that can hold the one goal slot and freeze its scope to the project's items. `deliver.sh` and the hook therefore still accept `owner/repo:feedback` (no go choice: it has no go field, shown as `go=unset`; no priority); everything else must be a project. A project link on the status page comes from the goal's mirror project (`block.project`), not from its spec.

**Goal ids after a repo rename (#792).** A goal id is `<owner>_<repo>-<kind>-<ref>` and names the repo as it was when the goal was registered. The repos were renamed (`scheduler` is `benjis-ops-tool`, `benjis-quoting-tool` is `benjis-sales-tool`; `skills/ticket-intake/repo-aliases.txt` is the one alias list). New specs and ids use the current name even when the spec is typed with an old one (`goal_parse` / `goal_id`). An existing id that carries an old name is never rewritten (not in the registry, not under `$PIPE`, not on the status page): `_goal_find` treats an old-name id and its current-name twin as one goal (the open entry wins, then the exact id asked for). Nothing needs migrating. To see whether any goal still depends on the alias, run the read-only `skills/orchestrate/goal-id-audit.sh` (prints `<registry issue> <open|closed> <id> <current id>`, empty = none).

**Old checkout directories (#792).** `orch-<key>.repo` files and queue entries written before the rename name the old local checkout (`~/dev/scheduler`, `~/dev/benjis-quoting-tool`), which no longer exists; the supervisor logged `[answered] <path>#<N> — issue read failed: repo name not resolvable` for each. `repo_dir_current` (maps a missing old directory to its renamed sibling) and `repo_slug` (falls back to the alias list when no directory exists; a slug read from a live origin URL is never rewritten, so existing run keys stay valid) in `pipeline-lib.sh` resolve them everywhere the supervisor and `launcher.sh status` read a repo from a state file. No file needs renaming for this to work. The status page reads the same alias list (`build-runs-json.py`), so these runs publish the current repo instead of `other`. No file needs renaming; the one-time rewrite of the old paths is optional and is never run by the pipeline (the command is in the description of the pull request that closes #792).

## Check on a run

```bash
~/.claude/skills/orchestrate/launcher.sh status          # every recorded orchestrator: running/exited + latest issue marker
~/.claude/skills/orchestrate/launcher.sh status 547
~/.claude/skills/orchestrate/launcher.sh tail 547 40     # last 40 lines of the orchestrator's log
```

The issue's latest marker is the truth; the log is for diagnosing a stall. Stage logs the orchestrator writes are in `~/.claude/pipeline/state/run-<issue>-<agent>.log`, and its run log is `~/.claude/pipeline/runs.jsonl`.

## Resume after a crash

The supervisor handles this automatically now. If you need to force-restart immediately (instead of waiting for the next supervisor tick), just launch again — it clears any tombstones and restart state.

## Stop

```bash
~/.claude/skills/orchestrate/launcher.sh stop 547
```

Stops the orchestrator and writes a tombstone preventing auto-restart. A stage it already launched (e.g. fullstack-developer) keeps running and will still post its marker; relaunch afterwards to pick it up.

## Status board (issue #10)

Each host pushes a heartbeat (running/queued/held/restarting runs, capacity, last activity) to a shared status page whenever `skills/orchestrate/report-status.sh` decides something changed or the keep-alive interval elapsed. It is a silent no-op — no network call at all — until `~/.claude/pipeline/config.local.sh` sets both `STATUS_PUSH_URL` (the deployed status-page Worker's `/beat` endpoint) and `STATUS_PUSH_TOKEN` (this host's bearer secret); both come from the companion infra issue once it deploys. Never invoked directly by a call site — `launcher.sh`, `supervisor.sh` and `hooks/report-status-hook.sh` all go through `report_status_async` (`skills/orchestrate/run-state.sh`), which backgrounds it, redirects its output to `~/logs/pipeline/report-status.log`, and can't propagate a failure back to the caller.

The status page's human-facing routes now require Google sign-in against an allowlist
(`status-page/README.md` "Sign-in"); before that the page was public (no auth, `noindex` only),
and `POST /beat` is unaffected either way (its own bearer-token auth, untouched). Since issue #29 each run's **issue title and GitHub issue URL are published** on it (JP's decision, 2026-09-19), so `owner/repo` appears in the payload inside `runs[].url` and nowhere else. `launcher.sh` fetches the title once at launch (before the capacity check, so queued runs get one too) into `$PIPE/orch-<issue>.title`; `supervisor.sh` `do_launch` fetches it only if that file is missing. The reporter only reads the file — a beat never makes a network call for a title, and a missing, empty or unreadable file just means the run is sent without `title`/`url` and shows an empty Ticket cell.

`STATUS_REPO_ALIASES=("owner/repo:alias" …)` in `config.local.sh` still populates `runs[].repo` in the payload and `/status.json` — a repo absent from the map publishes as `"other"` — but the alias is no longer shown in the HTML table. See `config.local.example.sh` for the placeholder form.

## Rules

- Never `Agent(subagent_type: orchestrator)`, from any session. The `block-orchestrator-agent.sh` hook rejects it with no exemption; the script starts the orchestrator as the main agent of its own process (`claude --agent orchestrator -p`), so nothing needs that call.
- Extra instructions carry instructions, never claims of verified state ("already fixed", "returns 200") — the orchestrator rightly distrusts them and stalls.
- Never run the launch command in the foreground or with the Bash tool's `run_in_background` — the script already detaches with `nohup`.
- Do the other work JP asks for in this session as usual; the orchestrator is unaffected by what happens here.
