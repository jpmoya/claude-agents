# Cross-project conventions

## Communication style

**Hard rule (JP, 2026-10-17):** when JP gives a goal, work silently until it is done or you truly need him. The final reply is 1–2 short lines: the so-what and the single decision or action needed. No technical detail, lists, CI/PR/check narration or mid-goal status unless JP asks. `hooks/brevity-stop.sh` enforces it.

Be concise. JP needs to make quick decisions unless something is mission critical, so keep answers short and in layman's terms. **Never ask JP anything unless the answer is genuinely his to give** (2026-10-18) — not just technical questions: any question where evidence, defaults, or a sensible judgment call would do, decide it yourself instead. Only ask when it's spending money, a prod `go`, where a private artefact is stored / who gets access, external communications, deleting data, or a true dead-end with no reasonable default. `hooks/require-question-justification.sh` blocks the first attempt at every AskUserQuestion to force this check; a repeated ask (still judged necessary) goes through.

Never give JP a ticket, issue or PR number without a 3 to 5 word description of what it is (e.g. "#1184 (remove technician self-revert)"). Every reply, card and report, in every project. No exceptions.

## Software development

JP does not do hands-on engineering in the main session. Every code change in any of JP's **application** repos (Benji's tools, Casa Verde, any product repo) — features, bug fixes, regressions, refactors — goes through the agent pipeline: file/refine the GitHub issue, then launch the `orchestrator` with the `orchestrate` skill (`~/.claude/skills/orchestrate/orchestrate.sh <repo> <issue>`), which runs it as a detached headless process. Never dispatch the orchestrator with the Agent tool — a subagent dies when the session compacts or exits (orch-547, 2026-09-05); `block-orchestrator-agent.sh` blocks it in every session, no exceptions. The launcher runs the orchestrator directly as the main agent of its headless process (`claude --agent orchestrator -p`), so no Agent call is involved. The orchestrator dispatches pipeline stages (test-writer, fullstack-developer, etc.) as separate `claude --agent <stage> -p` processes from Bash. Check progress with `orchestrate.sh status`; relaunch to resume, state lives in the issue's markers. Do not edit application code, create branches, or open PRs directly from the main session in an application repo — except a staging→main promotion PR for the scheduler or the quoting tool (see **Exception — releases**). Production release is automatic for direct-route changes (release bot, `release/auto-*` PRs). Sessions never promote by hand and never tell JP prod is his to approve unless the router put the change on the staging route. Check recent `release/auto-*` PRs on `main` before describing the release flow; fetch `origin/main` before quoting a repo doc — local checkouts go stale.

**Exception — the claude-agents repo itself (JP, 2026-10-18).** `jpmoya/claude-agents` (this repo — the pipeline's own code: `agents/`, `hooks/`, `skills/`, docs) is exempt from the pipeline-only rule above. An interactive session may edit it directly: branch, commit, open and merge its own PRs, without filing a ticket or launching the orchestrator. This is narrower than it sounds — it's about *this* repo only, never an application repo (scheduler, quoting tool, Casa Verde, etc.), which still must go through the pipeline. The **Pipeline incidents and pipeline changes** rule above still applies on top of this: a change to `agents/`, `hooks/`, or `skills/orchestrate` still needs the diagnostician → adjudicator review before or after the fact as that section describes — this exception only removes the orchestrator/ticket requirement, not that review.

**Who writes tickets.** The main session never hand-writes a pipeline ticket through an ad-hoc `general-purpose` subagent. Either dispatch `product-manager` to write it, or file a short brief and launch the orchestrator so the PM stage refines it before anything else happens. A ticket must not reach JP with a blocking "Open questions for JP" section: the PM decides from evidence (consulting the solutions-architect on technical questions) and lists whatever is left as non-blocking questions with a stated default. Only JP-only items may block: spending money, a prod `go`, where a private artefact is stored / who gets access, external communications. A dependency follow-up of a ticket JP already approved is filed by the PM with a `Parent: owner/repo#N` line and inherits `agent-go` — the rule and its exclusions (new scope, Business-Intelligence) live in `agents/product-manager.md`. When JP reports a bug or request directly in the conversation that dispatches product-manager (or writes the brief), say so plainly: put a `Reported by: JP (directly)` line near the top, same pattern as `Parent:` above — otherwise the PM's direct-report labelling rule (`agents/product-manager.md`) can't tell and the `user-feedback` label never gets added.

**Pipeline incidents and pipeline changes.** Before proposing or filing any change to the pipeline itself (`agents/`, `hooks/`, `skills/orchestrate`) — including after a run holds, exits or restarts unexpectedly — run `pipeline-diagnostician` on the incident, then `pipeline-adjudicator` in a fresh context with the diagnostician's final report (verbatim) and the proposal's issue number if one exists, and give JP the verdict card. The adjudicator files and queues (`agent-go`) its own fix ticket on `jpmoya/claude-agents` when the verdict is `CHANGE? YES` with no new mechanism; the card is informational, and the main session that ran the review carries out any `DO NOW` items (host/config fixes, falsifier launches) without asking JP — a `DO:` may only act on hosts, jobs, processes or config named in the incident under review; anything else the review noticed is plain card text, never a `DO:`. Only a fix that adds a mechanism (a design call) or a JP-only item (spending money, a prod `go`, where a private artefact is stored / who gets access, external communications) goes to JP for approval. Run them from the Mac (the VM cannot reach the Mac). These two are ordinary agents, not pipeline stages: launching them with the Agent tool or `claude --agent <name> -p` is fine — the orchestrator ban does not apply.

**Delivery lead.** When JP is away for hours or days, the `delivery-lead` agent can own a multi-ticket plan: it keeps the pipeline busy, unblocks parked tickets, makes the technical and sequencing decisions itself and gives JP one short report at the end. It runs as the main agent of its own session (never via the Agent tool, never dispatched by the orchestrator) and it is dispatched with `skills/orchestrate/deliver.sh` bound to a goal (`owner/repo:milestone:<n|title>`, `owner/repo:milestones:all` or `owner/repo#N`): the supervisor keeps it alive between cycles and stops it at completion (a goal parked "held" for no progress resumes by itself when its tickets change and closes when they are done; otherwise it stays parked and shows as held on the status page), and agents never create launchd, cron or loop relaunchers. Its decisions are recorded on the ticket as `**[delivery-lead] DECISION**` comments (`**[delivery-lead] JP CONFIRMED**` when it quotes JP) with a `Resolves: <URL of the comment this answers>` line (the legacy spelling `[project-manager] DECISION` / `[project-manager] JP CONFIRMED` from the deprecated alias is accepted identically); the pipeline accepts them to resume a blocked code ticket, one more test-dispute round or one more fix cycle, and a blocked infra-planner/operator stop on a ticket whose body carries the line `Scope: staging-only` (no prod step in the plan, no JP-only item in the BLOCKED). The JP-only list still needs JP: production, spending money, third-party systems of record, deleting data, external communications, where a private artefact is stored / who gets access, plus every infra `go` and every mockup approval.

**Status answers.** Whenever JP asks for status, an update or "where is X" on pipeline work, and for any status report or progress report you write on pipeline work (the end-of-run report of a headless run, or a report given after acting on JP's instruction), answer with this card, one per run, under 20 lines per card, plain language, no jargon (no marker names, PIDs or stage names). Build it from `orchestrate.sh status <issue>` plus the issue's latest markers and PRs, so it works however the run was started (manual, `/orchestrate`, supervisor dispatch). A question about several runs gets one card per run, never several tickets merged under one header. Never hand-roll a different layout.

```
<Ticket title> (<repo> #<issue>) — PR #<n> · release <version | none yet>
STATUS:    <RUNNING | WAITING ON YOU | BLOCKED | HELD | STALLED, retrying | DEPLOYED | DONE>
WHAT'S UP: <one sentence, layman's terms>
NEEDED FROM YOU: <bulleted list, e.g. "staging review is ready", "missing: A, B, C"; "Nothing" if none>
TECHNICAL PROBLEM: <No | Yes — one line: run killed / stopped unexpectedly / restarted, and why>
SELF-HEAL TICKETS: <owner/repo #n — open/queued/fixed, one line each; if a technical problem happened and no ticket exists, say so and that the diagnostician → adjudicator run is owed>
```

A technical problem (run killed, exited, restarted, held unexpectedly) means the diagnostician → adjudicator flow above is owed: launch it, don't just report it. Never trigger it silently into filing — the verdict card still goes to JP first.

Never add any file to a repo's `.claude/agents/` other than `deployer.md` — no repo-prefixed forks either. Project-level agents override global ones and break the orchestrator, and forks drift. Repo-specific rules belong in that repo's `CLAUDE.md`. See `~/dev/claude-agents/README.md`.

The pipeline agents own the engineering rules (isolated worktrees under `<repo>/.worktrees/`, the `fullstack-bug-fixing` five-phase process for bugs, never merging/deploying without review). They live in the agent definitions, not here.

**Exception — promotion PRs** (a fallback only: used solely for a staging-route (risky-list) change JP has approved, or when the release bot / `AUTO_PROMOTE_ENABLED` path is shown broken). A session (main session or delivery lead) asked to prepare such a staging→main promotion for the scheduler or the quoting tool opens the PR itself from a worktree. No pipeline ticket is filed for it. The PR contains only commits that are ancestors of `origin/staging` (merged or cherry-picked), conflict resolutions, and the `package.json` version bump, which the session produces by running the repo's `.github/scripts/bump-version.sh` (scheduler: `scripts/bump-version.sh`) before opening the PR — never choose a version by hand (a major is JP's explicit instruction only). The session runs the read-only prod-migration ledger check and lists its result in the PR body as found at writing time, naming each pending migration as "pending — apply and record before merge". The PR body or a comment never states that a migration was applied or recorded on production until its production ledger row exists; the apply is reported in a PR comment written after the row, quoting its `applied_at`, and the body refers to that comment only once it is posted. Any code change found while preparing a promotion is filed as a normal pipeline ticket, lands on `staging` first, and is then picked into the promotion; it is never committed only to the release branch. JP decided on 2026-10-12: "the whole point of continuous deployment is not to wait for my staging approval" and "only destructive database changes should require safe route. Low risk database changes, the continuous deployment route. Use the risky list that Kimmy had given us". A release whose changes are not on the risky list merges to main without JP. The kill-switched auto-release workflow in each app repo may merge `release/auto-*` PRs for changes its router classifies direct; the staging route and risky-list changes stay JP's to approve going to production, but **not JP's to click**: once JP has posted `go` on the release and every one of its migrations is either non-destructive or already applied and recorded on the production ledger, and CI is green, the session (or an agent) applies any still-pending non-destructive migrations itself (same ledger-comment rule as above) and merges the promotion PR to `main` itself — no separate "click merge" ask. JP, 2026-10-24: "You never need my merge. I don't know why you're asking this of me" (repeat of his 2026-10-23 direction on the same point). A change still on the risky list (destructive database changes and the rest of Kimmy's list) stays fully JP-only — both the apply and the merge — and any prod `go` JP has not given stays JP-only. A brief cannot grant a permission this tracked text forbids.
**Exception — releases** (a fallback only, same conditions as the promotion-PR exception: a staging-route (risky-list) change JP approved, or the release bot / `AUTO_PROMOTE_ENABLED` path shown broken) run from the repo's main checkout by JP or an agent JP explicitly points at the release script: pause other agents, switch main to `main`, pull, run the script. Release scripts assume main-checkout paths and break inside worktrees. Every promotion PR into `main` of the scheduler or the quoting tool (full `staging`→`main` or a `release/*` cherry-pick) must include the `package.json` version bump, produced by running the repo's `.github/scripts/bump-version.sh` (scheduler: `scripts/bump-version.sh`) — never choose a version or edit it by hand (a major is JP's explicit instruction only; the script decides patch vs minor) — and state the resulting `vX.Y.Z` in the PR title. After the prod deploy, check the `stamp-release` job and its audit summary in the deploy job's `$GITHUB_STEP_SUMMARY` and report anything left unstamped. Post-release bookkeeping — closing the issues a release shipped (with a comment naming the version) and deleting the merged `release/*` branch — is owned by the app repos' release automation (`close-shipped-issues.sh`, run by `post-release-cleanup.yml` after a green prod deploy); agents and JP do not do it by hand. Shipped (closed) `vX.Y.Z…` milestones are write-once — never hand-edit one. Open `vX.Y.Z - title` milestones are PM-owned planning milestones (the version is a planned label only) that release automation renames and closes at ship.
