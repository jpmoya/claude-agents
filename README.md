# claude-agents

JP's shared Claude Code config, synced across machines (Mac + Clog VM). Despite the name it now holds everything global, not just agents.

| Path | Symlinked to | Contents |
|---|---|---|
| `agents/` | `~/.claude/agents` | pipeline agent definitions |
| `hooks/` | `~/.claude/hooks` | hook scripts (all cross-platform; `cap-heavy-commands.py` is VM-only and wired from the VM's local settings if wanted) |
| `skills/` | `~/.claude/skills` | user skills |
| `CLAUDE.md` | `~/.claude/CLAUDE.md` | global instructions |
| `settings.json` | `~/.claude/settings.json` | shared settings: permissions, cross-platform hooks, skillOverrides, marketplaces, effort/advisor |

**Machine-specific settings stay in `~/.claude/settings.local.json`** (not tracked): model, theme, tui, plugin toggles, notification-sound hooks, `outputStyle`, `disabledMcpjsonServers`. Claude Code merges it over `settings.json`. Secrets never go here — `~/.claude/mcp-servers/`, `.mcp.json`, memory and `~/.claude.json` stay local.

- A `SessionStart` hook (`hooks/sync-agents.sh`) runs `git pull --ff-only` here, so every session starts with the latest config, and prints a warning if any symlink has been replaced by a real file.
- To change anything: edit here (or through the symlink), commit, push. Other machines pick it up on their next session.
- **No repo-local agents.** A repo's `.claude/agents/` holds at most `deployer.md`, which the orchestrator looks for locally. Nothing else: project-level agents override user-level ones, so a local `code-reviewer` silently replaces the pipeline one, and a repo-prefixed fork drifts from the global definition (casa-verde-site's did, 2026-09-03). Repo-specific rules go in that repo's `CLAUDE.md`, which every global agent reads.

## Install on a new machine

```bash
git clone https://github.com/jpmoya/claude-agents.git ~/dev/claude-agents      # any path; the VM uses ~/claude-agents
~/dev/claude-agents/skills/orchestrate/install.sh --minute odd --repos-base ~/dev   # even on the VM; add --scan on exactly one machine
```

`install.sh` is idempotent (re-run it after any pull): symlinks `agents hooks skills CLAUDE.md settings.json` into `~/.claude/`, creates `~/.claude/pipeline/config.local.sh` from `skills/orchestrate/config.local.example.sh` (edit `DISPATCH_REPOS` to what this machine may run from the `agent-go` pool; leave empty for hand-launch only — that list is the machine's **dispatch eligibility**), trusts every listed checkout in `~/.claude.json` (headless runs ignore `permissions.allow` in untrusted checkouts), installs the supervisor cron on the phase you chose (machines must alternate even/odd so ticks interleave) and the hourly scan if `--scan`, and lists what still needs you: `gh auth login`, `vercel login` (infra track), and `~/.claude/settings.local.json` (model, theme, and the `env` block with `SUPABASE_MGMT_PAT` / `SUPABASE_SERVICE_ROLE_KEY` for headless agents). **Scan coverage** is a separate matter from dispatch eligibility: on the one `SCAN_BACKLOG=1` machine the hourly scan covers that machine's `DISPATCH_REPOS` plus `SCAN_ONLY_REPOS` (default empty; scanned, never dispatched — the supervisor never reads it). The quoting tool is scanned on the VM through `SCAN_ONLY_REPOS` and dispatched only from the Mac. Business-Intelligence is in neither the scan nor any automatic queue — the Mac launches it only after JP himself adds `agent-go`. Secrets go only in `config.local.sh` (Slack webhook for the scan; `SLACK_BOT_TOKEN` and `SLACK_ENGINEERING_CHANNEL` for #engineering notifications, silent until both are set) and `settings.local.json` — never in the repo.

Machine-local, by design: `~/.claude/pipeline/config.local.sh`, `~/.claude/settings.local.json`, the crontab, `~/.claude.json` trust flags, `/tmp/pipeline` run state, `~/logs/pipeline`. Everything else a machine needs is in this repo.

**One more manual step this repo can't automate**: the Slack relay agent's identity lives outside this repo (`~/.openclaw/agents/pipeline-bridge/agent/IDENTITY.md`, openclaw config). Copy `skills/orchestrate/pipeline-bridge-prompt.md`'s content into that file so the relay knows to call `pipeline-bridge-dispatch.sh` instead of composing freeform shell from Slack text.

Pipeline: product-manager → ux-flow-designer (UI tickets: user flow — screens, states, copy) → ui-ux-designer (UI tickets: mockups of that flow, JP approval gate) ∥ solutions-architect (architecturally significant tickets) → **test-writer** (failing tests + stubs from the ACs, committed to the feature branch) → **test-reviewer** (pre-implementation: AC coverage, falsifiability) → fullstack-developer (implements against the locked tests; may add tests in new files, never edits locked ones — enforced by `hooks/protect-locked-tests.sh` + the orchestrator's byte-identical diff) → code-reviewer [+ test-reviewer narrow, only on added tests] → deployer (global; a repo may override with its own `deployer.md`). Staging-model caveat (scheduler and quoting tool, same two-Vercel-project / two-Supabase-project structure): feature branches come off `staging`, PRs target `staging`, the deployer merges to `staging` only — staging migrations, Actions deploy, E2E — and JP promotes `staging` → `main` to production himself; the deployer never touches `main` in those repos. `orchestrator` dispatches stages by reading routing-marker comments on the GitHub issue, and launches each stage as the main agent of its own headless process (`claude --agent <agent> -p`, never a "use the X subagent" wrapper session). **Comment protocol:** every agent starts every comment with `**[agent] ` + one of its routing markers on line 1 (e.g. `**[deployer] DEPLOYED**`), or `**[agent] NOTE**` for anything else (the orchestrator skips NOTEs). The vocabulary lives in one place, `hooks/pipeline-markers.sh`, shared by the handoff hook, the orchestrator's `markers`/`count` helpers and the supervisor: a first line outside it (`**[deployer] MARKER** PASS`, `**[deployer] COMPLETED**`) is inert — it never changes state and never satisfies the hook, whose nag names the agent's real markers. A new marker must be added there as well as to the agent definition and routing table. The orchestrator reads first lines only (jq), never the full thread. `hooks/require-handoff-marker.sh` (Stop/SubagentStop) refuses to let a stage finish until its marker is on the issue, using the `PIPELINE_ISSUE/AGENT/REPO` coordinates the orchestrator exports per launch; a no-marker run gets one handoff-only recovery dispatch before it's reported. `orchestrator` and `deployer` run on Sonnet (mechanical stages); the rest inherit the session model. The orchestrator itself is launched headless via `skills/orchestrate` (never as a subagent — `hooks/block-orchestrator-agent.sh` enforces it). A cron-based **supervisor** (`skills/orchestrate/supervisor.sh`, every 2 min on both machines — VM even minutes, Mac odd) does everything in one tick: restarts exited non-terminal orchestrators with backoff (120s/300s/900s/1800s; transient exits get a longer table), drains the local queue, caps at 3 concurrent (memory-aware: 1200MB floor), drops `agent-in-progress` on runs that finished or parked, and — where the machine's untracked `~/.claude/pipeline/config.local.sh` lists `DISPATCH_REPOS` — launches one open `agent-go` issue per tick after winning a claim (a `**[supervisor] NOTE** claim: <host>` comment; earliest in 10 min wins). Label rule: `agent-go` = approved and unlaunched; launching anywhere swaps it for `agent-in-progress`; the supervisor removes that when done/held. The launcher refuses issues owned elsewhere (`--force` overrides). Human gates (MOCKUPS PENDING APPROVAL, AWAITING GO) and BLOCKED past a 20-minute grace park the run as `held` with an alert; escalation after 3 no-progress or 6 total restarts posts a `**[supervisor] NOTE**` and holds too. `orchestrate.sh stop` writes a tombstone preventing auto-restart; a manual relaunch clears tombstones, `.restarts`, and `.alert` files and supersedes a queued entry. Mac dispatch runs only on AC power. Orchestrator processes run with `oom_score_adj=300` (Linux) so the kernel evicts them before interactive sessions. Logs append (`>>`) across restarts with separator lines, so prior-run evidence survives for diagnosis. The drain queue checks tombstones before launching, and `escalate()` purges the queue entry, preventing zombie relaunches of held issues. BLOCKED markers get a 20-minute grace period (`GRACE_PERIOD_SECS=1200`) before being treated as terminal — this prevents false-BLOCKED races where a subagent posts BLOCKED prematurely while its work is still completing (incident: #163, 2026-09-07).

**Fast lane (2026-09-08).** The PM writes a mandatory `Lane: fast | full` and a strict `UI change: yes | no` (back-end-only work is always `no`; the orchestrator never guesses). Fast-lane tickets — bug fixes, small changes, copy/link/config — go product-manager → fullstack-developer in fast-lane mode (writes its own regression test via `fullstack-bug-fixing`) → code-reviewer + test-reviewer narrow on Sonnet → deployer, skipping UX, SA, test-writer and the lock. Stall policy: the orchestrator polls every 15s, stops the moment a stage process dies, and caps a silent live process at 10/15/30 min by stage (one extension if the log is still moving), then kills it and runs handoff recovery.

**Infra track.** Issues labelled `infra` (DNS, Vercel domains/env/redirects, Supabase auth config, webhooks, API keys, workflow config, credential rotation) fork at the orchestrator to a separate roster with the same marker protocol: `infra-planner` (read-only inventory, then a runbook on the issue — per step: command, expected, verify, rollback, env, dependencies) → `infra-reviewer` (checklist review + spot-checks, `PLAN PASS` / `PLAN FAIL: n`) → `infra-operator` (executes verbatim; staging unattended, prod steps wait for JP's `go` comment on the issue; any Verify mismatch runs that step's rollback and posts `BLOCKED`; a `Blocked by:` issue still open at pre-flight also posts `BLOCKED`, runs no step, and parks the ticket until the dependency closes). No tests, no PR, no branch on this track; work needing both code and infra is two issues. Patterns borrowed from davila7/claude-code-templates' bicep-plan/bicep-implement split and terraform-iac-reviewer's plan/apply discipline (2026-09-08).

**Effort tiers (2026-09-08).** Every agent sets `effort:` in its frontmatter, overriding the shared `effortLevel: high` (which stays for interactive sessions): `low` for mechanical stages (orchestrator, deployer, infra-operator), `medium` for spec and checklist stages (product-manager, ux-flow-designer, test-reviewer, infra-reviewer), `high` for design and implementation (solutions-architect, test-writer, fullstack-developer, code-reviewer, infra-planner, ui-ux-designer). Fast-lane reviewer launches add `--effort medium` alongside `--model sonnet`. The solutions-architect and ui-ux-designer have **no fixed tier**: the PM recommends `Effort: medium | high | xhigh` per ticket from a complexity rubric and the orchestrator passes it as `--effort` on launch; `max` needs JP's approval (PM posts `EFFORT APPROVAL NEEDED`, JP replies `effort <level>` on the issue).

Why tests are authored separately: tests written by the implementer inherit its misreading of the spec (AgentCoder, arXiv 2312.13010). Independent authoring plus a mechanical lock means the test review runs once, early, instead of after every fix cycle.

**Status board (issue #10, 2026-09-17).** Each host's supervisor tick, `orchestrate.sh` launch/stop, and pipeline-stage hook push a heartbeat (`skills/orchestrate/report-status.sh`, fire-and-forget via `report_status_async` in `skills/orchestrate/run-state.sh`) to a shared status-page Worker on change or a keep-alive interval — silent no-op on any host missing `STATUS_PUSH_URL` / `STATUS_PUSH_TOKEN` in its untracked `~/.claude/pipeline/config.local.sh` (both come from the companion infra issue once it deploys the Worker + KV namespace). The status page is public (no auth, `noindex` only), and since issue #29 each run's **issue title and GitHub issue URL are published** on it (JP's decision, 2026-09-19): the title is captured once at launch into `$PIPE/orch-<issue>.title` and the reporter only reads that file — a beat never makes a network call for it. `STATUS_REPO_ALIASES=("owner/repo:alias" …)` in `config.local.sh` still populates `runs[].repo` in the payload and `/status.json` (unmapped repos publish as `"other"`), but the alias is no longer shown in the HTML table — see `skills/orchestrate/config.local.example.sh`. Deployed (issue #12): live page <https://status-page.jpmoya.workers.dev> — Worker `status-page`, KV namespace `STATUS` (id `251e3cc206b14ea7a78b3bb17f8ea1e3`, not a secret), workers.dev subdomain `jpmoya`; token values are never recorded here.

**Incident review (issue #27, 2026-09-19).** Two on-demand agents sit outside the pipeline and are run before any change to the pipeline itself (`agents/`, `hooks/`, `skills/orchestrate`). `pipeline-diagnostician` (read-only) confirms the root cause of an incident from logs, run state and source on both hosts — evidence before hypothesis, at least two rival mechanisms, numbered claims that each carry a citation and a reproducing command — and proposes no fix. `pipeline-adjudicator` then runs in a fresh context on that report verbatim: it re-runs every citation and strikes what does not reproduce, checks recurrence, judges the proposed fix as root-cause fix or symptom patch (complexity budget: net new mechanisms per fix = 0), and gives JP a plain-language verdict card; JP decides, and any change goes through the normal issue → orchestrator route. They are not stages: the orchestrator never dispatches them and they post no markers. The GitHub tickets are the record of the verdicts: the adjudicator's only write is one `**[pipeline-adjudicator] NOTE**` comment carrying the card — on the proposal issue if one was given, else on the incident's own issue when the verdict is `CHANGE? NO`; on a `CHANGE? YES` with no proposal and no new mechanism it files the fix ticket on `jpmoya/claude-agents` itself (card at the top of the body, labelled `agent-go`, skipped if a ticket for that incident already exists), so that ticket is the record; a `CHANGE? YES` that adds a mechanism files nothing and waits for JP. Scorecard, read off the `**[pipeline-adjudicator] NOTE**` comments and verdict-card issue bodies: the share of verdicts that were `CHANGE? NO`, the share of `IF IT WORKS` signatures that stopped recurring, and claims struck per verdict — zero struck over many verdicts means rubber-stamping.
